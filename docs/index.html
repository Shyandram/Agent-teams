The problem

A stalled agent looks
exactly like a working one

Run five agents in parallel and the hard part stops being the work — it becomes noticing which of them quietly stopped. An agent waiting on a permission prompt nobody can answer produces the same silence as one that is thinking.

agent-teams statusshop

!blockedneeds youWaiting on a permission prompt. Never resolves on its own — this is the one that costs an afternoon.
xerroredneeds youQuota exhausted, auth expired, or crashed. A rate-limited role stops producing output, which from outside is identical to having finished.
>workingActively producing. The transcript is still moving.
-idleAlive, nothing in flight. Waiting for work or for a message.
.stoppedSession ended. Its result block and token spend are still readable.
?unknownDeclared in the team manifest but never started.

Two modes

Native teammates cannot
be spawned headlessly

A -p session never spawns them — a native Claude team needs an interactive TTY. That constraint, not a preference, is why there are two modes at all. Anything that has to run in the background, survive an SSH disconnect, or span runtimes cannot use the native mechanism.

Mode A— in-session, interactive, Claude only

agent-teams launch --mode native

Spawns nothing. It checks the setup and prints the exact recipe to paste into an interactive session, because only Claude-inside-a-session can create teammates. Those teammates get the native SendMessage mailbox and the shared task list.

Mode B— detached fleet, all runtimes, the default

agent-teams launch --layout bg     # background + logs
agent-teams launch --layout tmux   # interactive windows

One OS process per main-task general, so Claude Code, Codex and pi can host independent sessions in one team. The general owns the session; research, engineering and QA roles are delegated subagents inside it. --layout tmux keeps each main-task session alive across SSH disconnects, so you can take one over mid-flight.

agent-teams attach lead   # drop into the main-task session and type at it

Both modes share the same role library, the same AGENTS.md, and the same coordination protocol. They are the interactive and the detached form of one team, not two products.

One session, many roles. The generated manifest marks the main-task general with session: true and attaches child roles with parent: lead. Only the general creates a runtime session; a child role can delegate further subagents without multiplying top-level sessions.

Ideas need approval first. An idea-general starts as approval: proposed, so it creates no session. After the main general reviews and changes it to approved, the next launch activates it. Three approved ideas plus the main general produce four sessions.

Composition

Parallelism only pays when
instances own different work

Two researchers with the same brief do the job twice. A catalogue of 66 assignments across 11 roles attaches by suffix, so each instance starts knowing what is its own.

# three researchers and two analysts, each on a different slice
agent-teams init --kind research \
  --roles "lead,research:survey,research:data,analysis:primary,analysis:ablation,qa"

# or two squads, each owning one direction end to end
agent-teams init --roles "lead,qa" \
  --squad "attn:research,analysis,engineering" \
  --squad "conv:research,analysis,engineering"

Squads decide internally without the lead, and are told not to converge on each other. If every squad lands on the same approach, the parallelism bought nothing.

Presets are deliberately small — solo 1, app-dev 3, research 4 — with -wide variants for work that genuinely splits. Every role is another full context to pay for and another thing that can wedge, so init warns above six.

Coordination

Messages are files,
so nothing is lost with a session

Roles talk through a file-based JSON mailbox rather than through a runtime feature. Codex and pi roles therefore participate identically to Claude ones, and a message outlives the session it was addressed to.

agent-teams send qa "auth landed at src/auth.ts:88 — re-run the suite"
agent-teams broadcast "freezing main in 10 minutes"
agent-teams steer engineering "stop, the spec changed"
agent-teams inbox                  # unread counts for every role

Nothing interrupts a running agent mid-turn. Delivery is at the recipient's next inbox check, and every role prompt tells it to check after each unit of work. The single exception is steer on a --layout tmux role, which types into the pane and lands immediately.

A message is information, not authority. It cannot expand a role's permissions, override AGENTS.md, or authorise an irreversible action — a role that receives one is told to decline and to say so in its coordination note.

Write access

One role, one branch

Each role owns exactly one branch, named from its instance so it is stable without another field to drift. It may commit and push there freely — small, self-describing commits as it goes, rather than one silent batch at the end. It may push nothing else.

agent/<role>       # yours — commit and push as often as you like
main               # denied
agent/<other>      # denied — read it, fetch it, diff it, never write it
git push --force   # denied everywhere, --force-with-lease included

Prefix matching cannot scope a push to one branch, so the deny list catches force-pushes, deletions and pushes to main, and the one-branch rule itself lives in the contract and in every role's prompt. Merging is not the role's call: it names the branch in its result block, and a human decides what gets integrated.

Observation

Read-only by construction

Python 3 standard library — no pip, no Node, nothing to stand up. It binds 127.0.0.1 and defines no do_POST: writes return 501 because the handler does not exist, not because a check remembered to reject them. There is no authentication, so reach it through a tunnel and not through --bind 0.0.0.0.

agent-teams monitor -C <project>   # [--port 8787] [--refresh 2]

# from the laptop
ssh -L 8787:localhost:8787 user@your-linux-box

It never blanks. When a collector goes unreachable the page keeps the last known rows behind a staleness warning, because an empty table would read as nothing running — the exact lie the tool exists to prevent.

claude agents --json

pid, status, state and session id for each Claude session in the project. No TTY required.

Session transcripts

The last 256 KB of the session JSONL; whole files reach tens of megabytes. An agent that relocated into a git worktree writes its transcript under the worktree's slug, so the collector falls back to a worktree glob rather than losing it silently. claude logs is deliberately not used — it replays the raw TUI stream, which redraws in place and does not survive stripping.

Codex rollouts

Rollout files matched on the session's recorded working directory, scanned for errors and failed turns. Live sessions that no role in the manifest claims are still shown, marked unmanaged: hiding a blocked stray would be a lie by omission.

A runtime state it does not recognise degrades to unknown and emits a warning naming the value, so the dashboard never invents a state it does not understand. agent-teams status --json emits the same payload as GET /api/state.

The honest part

Four ways a fleet dies quietly

All four were found by running real fleets, not by reading documentation. Every one of them looks, from the outside, like an agent that is still working.

Untrusted directory

A background session in a directory that has never been trusted blocks on its first write — even with acceptEdits. launch refuses to start rather than spawning agents that wedge, and never sets the trust flag for you: that is a security control.

Chained commands

Permission matching applies to the whole command, so git add X && git commit matches neither an entry for git add nor one for git commit. The contract tells roles to issue one command per call — allowlisting every compound form is unwinnable.

Quota exhaustion

A rate-limited role stops producing output, which is indistinguishable from having finished the job. Rendered as errored, never as idle, and a hook can fire on it.

Work on a side branch

A background agent may relocate itself into a git worktree and commit there, so its work is not in your tree. close refuses to disband while commits sit in a worktree, and names which.

Teardown

close reviews before
it tears anything down

Disbanding is where work goes missing, so close reviews first and refuses rather than proceeds. Each refusal names what it found.

!role runningA session is still live. Stop it, or read what it is in the middle of.
!note openA coordination note is unfinished — that role never recorded how its work ended.
!worktree commitsCommits are sitting in an agent worktree, which means they are not on your branch. It names which, so you can look before deciding.
agent-teams close             # review, then refuse if work would be lost
agent-teams close --dry-run   # the review only
agent-teams close --force     # proceed anyway

When it does proceed it stops every session, removes the tmux session, and writes a closeout report giving each role's final state, its token spend, and what was left unresolved. Logs, notes and worktrees are always kept.

Install

One symlink

Claude Code and Codex read the same SKILL.md format, so one directory serves both. The CLI also works standalone by absolute path.

git clone https://github.com/Shyandram/Agent-teams.git ~/skills/agent-teams
bash ~/skills/agent-teams/agent-teams/install.sh

# then, in a project
agent-teams init --kind app-dev     # contract, aim, roles, permissions
agent-teams doctor                  # runtimes, auth, tmux, workspace trust
agent-teams launch --layout tmux    # survives disconnect; take a role over
agent-teams monitor                 # 127.0.0.1:8787

# from a laptop — the dashboard binds loopback and has no auth
ssh -L 8787:localhost:8787 user@your-linux-box
